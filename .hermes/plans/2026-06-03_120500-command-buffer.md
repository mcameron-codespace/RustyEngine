# Implementation Plan: Decoupled Component Command Buffer

**Date:** 2026-06-03  
**Status:** Draft / Not started  
**Goal:** Introduce a typed, bounded command-buffer abstraction for communication between engine subsystems so producers (physics, input, gameplay) never call consumer APIs directly.  
**Constraints:**
- No `unsafe` blocks.
- No blocking wait in producers; consumers drain on their own schedule.
- Backward compatible with the existing `crossbeam_channel` usage; this is a higher-level wrapper, not a replacement.
- Keep existing tests passing after every batch.

---

## Current context / assumptions

- The repo already models decoupled comms in two places:
  - `src/audio/bridge.rs` – `PhysicsAudioBridge` sends `AudioCommand` over `crossbeam_channel::Sender`.
  - `src/network/` – mock socket reads into `incoming_packets: VecDeque<Vec<u8>>`.
- The plan mode is active; this file is the only artifact produced in this turn.

---

## Proposed approach

1. **Define a typed `Command<T>` enum** with a bounded set of payloads (no open-ended `Box<dyn Any>`).
2. **Introduce a `CommandBuffer<T>` struct** that owns:
   - a bounded ring buffer for commands produced on one thread,
   - a draining mechanism for consumers,
   - back-pressure semantics when the buffer is full.
3. **Add three component-specific command channels** using the same primitive:
   - Audio commands: `AudioCommand` (existing shape).
   - Render commands: `RenderCommand` (submit draw calls, resource updates).
   - Input/Gameplay commands: `GameplayCommand` (pause, spawn, scene transitions).
4. **Wire them into a central `CommandDispatcher`** so subsystems can register producers/consumers without direct references to each other.

This is additive; no existing call sites must change to compile.

## Step-by-step plan

### Batch 1 — Core command buffer primitive
- Create `src/commander/buffer.rs`:
  - `Command { id: u32, payload: T }`
  - `CommandBuffer<T>` with:
    - `with_capacity(usize) -> Self`
    - `push(Command<T>) -> Result<(), Command<T>>` (returns full command)
    - `drain() -> impl Iterator<Item = Command<T>>`
    - `len()`, `is_empty()`, `clear()`
    - Optional `is_full() -> bool`
- Use a simple `Vec<Option<Command<T>>>` ring with head/tail indices to avoid extra deps.
- Add `src/commander/mod.rs` to export.

### Batch 2 — Audio bridge migration
- Refactor `src/audio/bridge.rs` to use `CommandBuffer<AudioCommand>` instead of the raw `crossbeam_channel::Sender<AudioCommand>`.
- Expose `audio_buffer: CommandBuffer<AudioCommand>` on the audio system struct.
- Keep the old sender API behind a feature flag? Actually: prefer a clean wrapper with a single path; deprecate direct sender usage by moving the channel behind a `try_send` helper.
- Update `src/audio/mod.rs` consumers.

### Batch 3 — Render and gameplay command types
- Add `src/renderer/command.rs`:
  - `enum RenderCommand { DrawMesh { entity: Entity }, UpdateTransform { entity: Entity, transform: Transform }, Clear }`
- Add `src/gameplay/command.rs`:
  - `enum GameplayCommand { SpawnVehicle { position: [f32;3] }, Pause, Resume, SetCheckpoint { index: u32 } }`
- Create `CommandBuffer<RenderCommand>` and `CommandBuffer<GameplayCommand>` inside their respective modules.

### Batch 4 — Central dispatcher
- `src/commander/dispatcher.rs`:
  - `struct CommandDispatcher { audio: CommandBuffer<AudioCommand>, render: CommandBuffer<RenderCommand>, gameplay: CommandBuffer<GameplayCommand> }`
  - `fn dispatch(&mut self, cmd: impl Into<AnyCommand>) -> Result<()>` — concrete target per enum.
  - Typed accessors: `fn audio(&self) -> &CommandBuffer<AudioCommand>` etc.
- Update `src/commander/mod.rs` to re-export.

### Batch 5 — Integration updates
- Update `src/physics/state.rs` step callback to post `AudioCommand::PlaySpatialEvent` via dispatcher instead of `audio_sender.send(...)`.
- Update `src/network/rollback.rs` to post `GameplayCommand::SetCheckpoint` via dispatcher.
- Update `src/gameplay/mod.rs` to consume `GameplayCommand` from dispatcher.
- Update `src/renderer/mod.rs` render loop to consume `RenderCommand` before drawing.

### Batch 6 — Tests & validation
- `src/commander/buffer.rs` tests:
  - push up to capacity succeeds.
  - push beyond capacity returns the command unchanged.
  - drain empties the buffer and yields commands in FIFO order.
  - `clear` resets state.
- Update `src/audio/bridge.rs` tests:
  - collision events produce commands in buffer, not on the channel.
- `cargo test` after each batch.

## Risks, tradeoffs, and open questions

1. **Back-pressure semantics** — If the producer outruns the consumer, we either drop new commands or overwrite oldest. The plan chooses “return the command to the producer” so the producer can decide.
2. **Allocator choice** — A `Vec<Option<Command<T>>>` ring is simple but uses `Option` slots; an alternative is `smallvec` + head/tail slices for fewer branches.
3. **Batching vs single-command dispatch** — The dispatcher should probably support batch drain per frame to reduce lock-step overhead.
4. **Async boundaries** — If any consumer wants `async`, the current sync ring buffer needs an async-aware variant; out of scope for this batch.
5. **Thread safety** — The buffer is `!Sync` for now; if needed, wrap with `Mutex` at the dispatcher boundary rather than inside the buffer.
